# 工作流模块：不变量与踩过的坑

这份文档记录的是**代码本身看不出来的约束**——每一条都对应一个真实修过的 bug 或一次失败尝试。
改工作流相关代码前先扫一遍，能避免重犯。

## 一、存盘（`src/workflow/store.js`）

**写盘永远不能抛异常。** `saveRun` 在引擎里每个节点状态变化时都被调用，抛一次就会终止整次运行。
- `JSON.stringify` 也必须包在 try 里（循环引用 / 超大对象 / 内存不足都会抛）
- rename 在 Windows 上会因索引器/杀软占用而 `EPERM`：临时文件名带进程+时间+随机数，
  rename 失败重试 5 次退避，仍失败退化为直接覆盖写
- **一条坏记录不能堵死后续所有落盘**：整体序列化失败时逐条筛，能写的照写、
  写不了的移出内存并记日志点名（否则那张表永远写不进去）
- 解析失败的文件先 `copyFileSync` 成 `.corrupt-<时间>.bak`，**绝不直接覆盖**——
  否则下一次保存就把损坏内容永久落盘，定义全丢
- 运行记录用合并写（250ms），子运行上限 30 条（`MAX_SUB_RUNS`），否则百项循环会让每次
  合并写都序列化上百条记录
- `process.once('exit')` 里补写时**不能 clearTimeout**，会撞 libuv 的
  `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)`
- **触发器状态要打补丁写**（`patchWorkflow`），不能走 `saveWorkflow`：
  后者会用请求里的 nodes/edges 整份覆盖，正好把界面正在编辑的那张图冲掉
- **模板单独一个文件**（`workflow-templates.json`），同样走原子写 + 损坏先备份；
  它的导出结构与工作流导出一致，所以「导入模板 / 导入工作流」复用同一条路径，
  不要为模板再写一套解析
- 主程序的任务记录（`server.js` 的 `tasks.json`）用 `saveStoreSoon()` 做 250ms 合并写，
  新建/删除等关键路径仍旧 `saveStore()` 立即写；退出钩子里补写最后一次，同样不能动定时器
- **预约任务的参考图落盘到 `data/refs/`**，记录里只留文件名：
  base64 原文塞进 `tasks.json` 会让文件随预约数量线性膨胀；
  `resolveRefBuffer` 读回来时要用 `path.basename`，否则记录里的相对路径能越出目录

## 二、引擎（`src/workflow/engine.js`）

**分支路由有三个前提，缺一个就静默出错：**
1. 边上的 `branch` 必须活过 `sanitizeDefinition`（曾经被丢掉 → 两条分支都执行）
2. `takenBranch` 必须校验节点类型是 `condition`——`merge` / `code` 会把用户字段展开到输出顶层，
   任意一个叫 `branch` 的字段都会劫持路由
3. `projectOutput` 的保留列表必须含 `branch` / `index` / `is_else`——
   用户在条件节点上声明任意输出参数后，路由信息曾被投影砍掉，
   导致命中分支的整条下游被静默 `skipped`、运行还报成功

**取消必须传播到子运行。** 循环体的子运行是独立记录，`tick` 会无条件重新 kick 未终态 run；
只标父运行会让剩下的子工作流继续烧配额。`cancelRun` 递归收集 `parent_run_id` 链。

**禁用节点是「透传」不是「掐断」。** 状态记 `skipped`，但输出=上游输出，且对下游算「已放行」；
否则下游会被一起跳过。

**从中间节点开始（`from_node`）**：上游标 `success + seeded`（输出取历史运行结果），
下游照常，**既非上游也非下游的平行分支必须显式标 `skipped`**——
不处理会留下悬空 pending 节点，运行以「有节点无法执行」失败。

**`incoming` 存的是 `{from, branch}` 对象不是 id 字符串**，改动这里要看所有使用者。

**并发推进（一次一批 ready 节点，上限 `WF_MAX_PARALLEL`，默认 4）**
- 「可以跑了」必须是**所有入边都定局**（`allSettled`）才算 ready。原先只要有一条入边
  被走到就判 ready，于是变量聚合这类多上游节点会在另一个上游还在跑的时候就启动，
  参数里引用到的那一边是空的。并发之后这个洞会被放大，所以一并收紧
- **被禁用节点的判定也要等上游定局**：它的「透传」值就是上游输出；早标一步会把
  透传值标成 null，下游拿到空值（并发改造时实测踩到：`[禁用节点]透传` 用例从通过
  变成 `outputs={}`，用老引擎对照才定位到）
- `executeNode` 失败且策略是「停止整个工作流」时会把运行直接标成失败，
  批内其它节点的结果照常落盘——这是有意的，不要为了"干净"去取消它们在跑的请求

**循环容器（`loop.params.body` = 被拖进框里的节点 id）**
- 循环体节点**不参与顶层推进**：`buildGraph` 过滤掉它们，`startRun` 把它们的顶层状态
  标成 `skipped` + `note='在循环体内执行'` + `in_loop=<循环节点 id>`；少任何一半，
  要么顶层重复执行、要么运行以「有节点无法执行」失败
- 每项的循环体定义是循环节点当场拼的：**用循环节点自己的 id 冒充内层「开始」**，
  这样循环体里写 `{{循环节点.item}}` 天然可用；再补一个「结束」把没有出边的节点当结果
- 出入口（roots/sinks）只按**这一层真正要执行的节点**算：框里套着循环时，
  内层循环体由内层循环调度，不能算成外层的出口（踩过：外层 end 的 outputs 变空）
- 嵌套要带**传递闭包**（`expandBody`）：内层循环体节点也要放进外层的临时定义里，
  否则内层循环在自己的子运行里找不到它的循环体
- 循环体节点在临时定义里的连线：指到框外的边丢掉，框内没有入边的接在内层「开始」上

**子工作流节点**：`depth` 记在子运行上（`runToCompletion` 的 `depth` 参数），
超过 5 层直接报错——这是「两个工作流互相调用」的唯一刹车；另外禁止直接调自己。

## 三、代码节点沙箱（`src/workflow/nodes.js`）

**只让字符串跨越宿主与沙箱的边界。**
- 输入用 JSON 字符串传进去、在上下文内 `JSON.parse`；日志与结果也在上下文内序列化出来
- 原因：`codeGeneration: {strings: false}` 只约束**上下文自己**的 eval/Function。
  一旦注入宿主对象（`Object`、甚至 `console.log` 函数），就能沿原型链
  `Object.constructor('return process')()` 爬到宿主。第一版修法就是这么失败的。
- **`vm` 不是安全边界**。Python 代码节点跑的是真实解释器，**完整系统权限**。
  因此：导入含代码节点的工作流要弹确认框；服务端默认只听 `127.0.0.1`。

**正则在主线程同步跑，没有 vm 超时保护。** 文本节点的 regex 模式必须限制模式长度、
源文本长度，并拒绝 `(…+)+` 这类灾难性回溯写法，否则一条工作流能卡死整个服务。

**变量路径允许中文**（`vars.js` 的 `VAR_PATH = [^\s{}]+`）。
老写法 `[A-Za-z0-9_$.[\]-]+` 遇到 `{{start_1.产品图}}` 会**整个不匹配**，
插值直接跳过、把 `{{...}}` 原样留在参数里 —— 表现是"变量没生效"，
而且不会报任何错，所以别再把它改回 ASCII 白名单。

## 四、HTTP 节点

`res.text()` 是先把整个响应读进内存。URL 常由变量拼出来，可能指向大文件或无限流，
所以改成**边读边计数、超 2MB 立即 `reader.cancel()`**，并输出 `body_bytes` / `truncated`。

## 五、触发器（`src/workflow/triggers.js`）

- Webhook 只有一把 32 位十六进制令牌，**令牌不对返回 404**（不是 403）：
  不泄露"这个工作流存不存在"；重置令牌后旧地址立刻失效
- 定时计划先归一化再用：最多 8 条、非法模式落回 `interval`、
  0/超大分钟数收口到默认或上限、`last_fired_at` 要跟着计划一起保存
  （否则"每隔 N 分钟"每次保存都会被重置成从现在算起）
- 调度器每 20 秒扫一次，**启动时先补扫一次**（客户端关着时错过的计划）；
  同一个工作流上一次运行还没结束就跳过这一次，不叠着跑（否则每 20 秒堆一个 run）
- 时间基准统一北京时间，不要用本机时区算「每天 HH:MM」

## 六、前端（`src/workflow-ui/`）

- `[hidden] { display: none !important; }` 是**承重墙**：视图切换靠 `hidden` 属性，
  重写样式表时删掉它会让所有视图同时显示
- 整个 `.wf-view` 禁用 `user-select`，输入框与 JSON 输出显式恢复——
  否则拖动时会扫出系统强调色的选区块，看起来像 bug
- **`snapshot()` 用去重**，焦点反复进出、空拖动不塞重复历史；
  参数改动靠 `focusin` 压快照（压的是改动前状态），编辑过程不压
- `saveCurrent()` 一进来就 `clearTimeout(state.saveTimer)`，
  否则「点试运行」与 900ms 自动保存并发、后写覆盖先写，跑的可能不是画面上的图
- `promptRun` 的输入项要读**画布实时图**（`state.canvas.getGraph()`）而不是
  `state.current.nodes`（打开时的旧副本），否则刚加的输入项不出现在表单里
- `canvas.destroy()` 必须移除挂在 window 上的 mousemove/mouseup，
  否则反复打开编辑器会累积监听
- 对齐吸附要以**拖拽起点坐标**为基准，用当前坐标会越拖越偏
- **节点高度只有 `nodeHeight(node)` 一个来源**（条件分支按出口数长高）。
  缩略图、框选命中、吸附、自动适配、居中、浮层定位都要用它；
  哪里写死 `NODE_H`，条件分支节点一长高那里就会错位
- 条件分支的出口列表从 `params.branches` **当场推导**（`branchesOf`），
  不要读 `node.branches` 那份缓存：它只在参数面板改动时才刷新，
  导入 / 粘贴 / 回放进来的节点那里是空的；改出口名时要按行序把边一起改名，
  否则改完名字线就悄悄掉回第一个出口
- 循环容器判定「拖出去」时必须**把被拖的节点本身从容器范围里排除**：
  容器是按成员算出来的，不排除的话它会跟着节点一起长大、永远判定为"还在里面"
- `openWorkflow()` 要**按需 mount**：从图片页「用工作流生成」这类外部入口进来时，
  工作流视图还没挂载，直接 `renderEditor()` 会往 null 上写 `hidden` 报错
- 弹窗不要用 `window.prompt`（Electron 不支持），用 `openDialog()`

## 七、验证纪律

- **先 `node --check`，通过才部署。** 这条顺序救过一次：把 `${...}` 嵌进模板表达式的对象字面量
  是非法 JS，检查拦下了，坏文件没进安装目录（否则整个工作流界面白屏）
- `wenVedio_Client/test/workflow.test.js` 是工作流的自包含回归测试（106 项断言），
  自己起服务端、跑完清理：`cd wenVedio_Client && node test/workflow.test.js`
  （端口被占用用 `WF_TEST_PORT=8796`）
- `wenVedio_Client/test/task-recovery.test.js` 是**主程序任务记录**的自包含回归测试（12 项断言）：
  重启后卡住的图片任务要判失败、能续查的视频任务不动、预约参考图落盘（tasks.json 里不能有
  base64）、状态频繁变化要走合并写（用例靠数文件 mtime 变化次数来断言）。
  它用 `WENVEDIO_ENV_FILE` 指向临时 .env 来开 `MOCK=true`，不碰真实平台
- 前端夹具是 `.tmp-ui/shot.js`：`SHOT_SET` 选步骤组，现有
  `versions`（版本抽屉）/ `branchports`（多出口圆点）/ `triggers`（触发抽屉）/
  `loopbody`（循环容器拖拽）/ `templates`（模板库）/ `imagewf`（图片页工作流入口）。
  两条例外：探针**必须返回 `JSON.stringify(...)` 字符串**（返回对象只会被记成
  `[object Object]`）；拖拽类交互用合成 MouseEvent（mousedown 派发在元素上、
  mousemove/mouseup 派发在 window 上）
- 测后端时先确认端口没被旧的 `node src/server.js` 占着——
  曾经因为旧进程还活着，新进程绑不上端口，测的其实是旧代码
- 用户正在用的客户端**不能动**：所有验证都在独立档案实例（`WENVEDIO_PROFILE=test`）上做

## 八、已知限制（不是 bug，是设计取舍）

- 图片生成节点在生成中途重启进程**无法续跑**（图片接口没有可续查的任务号），
  会明确报错让用户重跑；视频节点可以续跑。
  主程序里的图片任务同理：重启时会被 `recoverStuckTasks()` 明确判失败
  （图片任务走同步接口、没有可续查的任务号），而不是一直挂着「进行中」
- 子工作流的输入要能被接住，必须在它的「开始」节点声明同名字段——
  开始节点只透传声明过的输入
- `last_run_status` 等卡片统计存在工作流定义里，清理运行记录不会影响它们
- 定时触发依赖服务（客户端）在跑；关着的时候错过的计划只在启动后补最近一次
- 触发器的 Webhook 只有令牌鉴权、且是明文 HTTP；服务端默认只听回环
- 循环容器的归属按「节点中心是否落在框里」判定，拖到边缘时可能不符合直觉
- 模板库是本地的（文件分享），没有云端市集
